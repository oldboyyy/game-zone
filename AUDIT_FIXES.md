# Аудит и исправления GameZone

Дата: 2026-11-19. Это первый проход по критическим потокам, а не подтверждение отсутствия всех ошибок. Существовавшие до аудита незакоммиченные изменения сохранены.

## Проверенная архитектура

Клиент: Next.js 15, React 19, TypeScript, Redux Toolkit/RTK Query, Tailwind.
Сервер: Express, Prisma/PostgreSQL, Redis, Socket.IO, Stripe.
Слои сервера: маршруты → контроллеры → сервисы → репозитории.
Демо в localStorage и серверная база независимы.

## Исправления

- Корзина: изменение/удаление только позиций текущего пользователя или гостевой сессии. Проверяются целочисленные положительные количества в пределах PostgreSQL Int и наличие variantId.
- Объединение корзин: требуется авторизация; все изменения выполняются в одной транзакции; объединение корзины с собой ничего не меняет.
- Ошибки отсутствующего товара/позиции и недостаточного остатка возвращают ожидаемые 4xx вместо обычного Error/500.
- Адреса: контроллер читает параметр id, совпадающий с маршрутом. Удаление проверяет владельца.
- Платежи: удаление проверяет владельца.
- Отзывы: удаление доступно автору, ADMIN или SUPERADMIN.
- Создание отправления: только ADMIN/SUPERADMIN.
- Чат HTTP: читать и отправлять сообщения могут владелец и сотрудники; общий список и изменение статуса доступны только сотрудникам. Пустые сообщения без файла и неизвестные статусы отклоняются.
- Ответы чата содержат только id/name/avatar/role пользователей вместо полных записей с password.
- Socket.IO: проверка JWT и существования пользователя; доступ к комнатам по владельцу/роли; сигналы звонков ограничены участниками одной комнаты; соединение закрывается по истечении токена.
- Клиент чата передаёт cookies и повторно входит в комнату при соединении. Хук пользовательского чата возвращает socket через состояние React, чтобы подписчики получили созданное соединение.
- optionalAuth больше не превращает запрос с невалидным/истёкшим токеном в гостевой; 401 позволяет клиенту использовать обновление токена.
- Убрана отладочная печать заголовков, cookies, сессий и содержимого корзин из проверенных модулей.
- Пустые списки заказов, адресов и платежей возвращаются успешно вместо 404.
- Webhook принимает только оплаченную сессию и проверяет владельца корзины. Позиции/цены берутся из Stripe line items, а не из изменяемой корзины. Списание остатков условное и атомарное; счётчик продаж увеличивается атомарно. Сохраняются другие товары и добавленные сверх оплаченного количества единицы.
- Повторная конкурентная доставка webhook учитывает уникальность ID заказа. Ошибка подписи возвращает 400; отсутствие webhook secret — 503.
- Node.js 22 закреплён в engines корневого, клиентского и серверного пакетов; актуализированы устаревшие части README.

## Что ещё мешает считать проект завершённым

1. Валюта: checkout и общий форматтер используют KZT. Нужна проверка валюты существующих данных; настройка валюты интерфейса не конвертирует цены. Валюта в модели заказа отдельно не хранится. До согласования не использовать реальную оплату.
2. Оплата и остатки: условное списание предотвращает отрицательный остаток, но при одновременной покупке последней единицы платёж уже может быть принят. Нужны резервирование до оплаты либо гарантированная компенсация/возврат и обработка такого заказа.
3. Доставка: webhook теперь сохраняет shipping address из collected_information Stripe, включая строку квартиры; billing address не подставляется. Фиктивные отправления больше не создаются. Реальное отправление создаётся отдельным административным API. Полный жизненный цикл доставки ещё требует проверки.
4. Корзины: userId не имеет уникального ограничения; параллельные getOrCreateCart могут создать несколько корзин. Нужны анализ существующих дублей и аккуратная миграция. Одновременные операции добавления/слияния требуют интеграционных проверок.
5. Вебхуки: события корзины, очистка кеша и логи выполняются после транзакции; для гарантированной доставки побочных действий нужен механизм повторов/outbox.
6. Чат: нужны браузерные проверки звонков, загрузок и восстановления после истечения access token; автоматическое обновление авторизации сокета ещё не реализовано.
7. Остальные подсистемы (GraphQL, отчёты, экспорт, OAuth, восстановление пароля, загрузки, админские CRUD) требуют отдельного сквозного прохода. Этот отчёт не утверждает, что они полностью проверены.
8. Локализация, каталог и фильтры, единый дизайн, доступность и мобильные сценарии остаются этапом завершения продукта.
